# Detection Performance Evaluation (Recall & Precision)

This folder reproduces the human-annotated ground-truth evaluation of the PII retrieval
stage reported in the paper (**Section 5.2, Table 3**: *Detection Performance by Type:
Regex vs StarPII vs Combined*).

## Contents

| Path | Description |
|---|---|
| `run_recall_precision.py` | Runs the detection stage (regex + StarPII NER, **no LLM refine**) over the ground truth and computes per-type recall/precision for regex, StarPII, and combined. |
| `data/sample_redacted.jsonl` | A small, **redacted** sample (12 spans) illustrating the record schema. Real values, file contents, and repo paths are masked. |
| `data/groundtruth_pii_flat_min150.jsonl` | The full ground-truth set (**808 files, 1,689 spans**). **Not included in the public repository** — see *Data access* below. |
| `results/` | Generated by the script (see below). |

## Data access

The full ground-truth set is annotated real PII sampled from public source code, and therefore
contains live-looking credentials (keys, passwords) and other personal data. To avoid
republishing real secrets, the full file is **not committed to this public repository**; only
the redacted schema sample (`data/sample_redacted.jsonl`) is included.

To reproduce the numbers, download the full file `groundtruth_pii_flat_min150.jsonl` from the
archival record on Zenodo (<https://zenodo.org/records/21459384>) and place it at
`detection_eval/data/groundtruth_pii_flat_min150.jsonl`, e.g. from the repository root:

```bash
curl -L "https://zenodo.org/records/21459384/files/groundtruth_pii_flat_min150.jsonl?download=1" \
     -o detection_eval/data/groundtruth_pii_flat_min150.jsonl
```

The script expects the full file at that path.

### Ground-truth record schema

Each line in `data/groundtruth_pii_flat_min150.jsonl` is one labeled span:

```json
{
  "file_id": "...",           // file identifier (spans of the same file share it)
  "pii_type": "ip_address",   // one of: email, password, name, username, ip_address, key
  "value": "10.0.0.1",        // the annotated PII string; equals content[start:end]
  "location_start": 1234,     // char offset (inclusive) into content
  "location_end": 1242,       // char offset (exclusive) into content
  "content": "...",           // full source of the file
  "repo_name": "...",
  "path": "..."
}
```

Span counts per type: Email 223, Password 203, Name 228, Username 308, IP Address 458,
Key 269 (total 1,689).

## How to run

The detectors are imported from the project's `../src`, so this uses byte-for-byte the same
detection code as the dataset-construction pipeline. It needs the project environment
(`../requirement.txt`: torch + transformers) and a HuggingFace token with access to the
gated `bigcode/starpii` model.

Provide the token via the `HF_TOKEN` environment variable or a `.env` file at the repository
root (`HF_TOKEN=hf_xxx`), then run from the repository root:

```bash
python detection_eval/run_recall_precision.py
```

## Outputs (written to `results/`)

| File | Description |
|---|---|
| `metrics_table.md` | The Table 3 numbers (regex / StarPII / combined recall & precision by type). |
| `metrics.json` | The same numbers, machine-readable. |
| `samples.md` | Sampled true-positive / false-negative / false-positive spans with surrounding context. |
| `false_positives.jsonl` | Every combined false positive, for manual inspection. |
| `missed_combined.jsonl` | Every ground-truth span the combined detector missed. |

## Metric definitions

- **Match rule**: same `pii_type` **and** any character overlap.
- **Recall** (GT-centric): fraction of ground-truth spans with at least one overlapping
  same-type prediction. This is the trustworthy metric.
- **Precision** (prediction-centric): fraction of predictions overlapping at least one
  same-type ground-truth span. Because the ground truth is a curated, non-exhaustive set,
  a "false positive" may be a genuine PII span that was simply not part of the curated
  ground truth, so precision here is a lower bound, not a clean detector precision.

Regex covers only `email`, `ip_address`, and `key` (the structured, rule-governed types);
StarPII covers all six. See paper Section 5.2 for the discussion of this asymmetric design.
